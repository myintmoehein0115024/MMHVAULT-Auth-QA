## 二、关键发现：Cloudflare 三个部署设置不一致

Cloudflare Pages 项目 API `source.config` 实测：
- `deployments_enabled=true`：**旧版/已弃用的总自动部署开关仍为 true**。
- `production_deployments_enabled=false`：新版生产分支自动部署开关已关闭。
- `preview_deployment_setting='none'`：新版预览分支自动部署已关闭。

Cloudflare OpenAPI 中 `deployments_enabled` 的描述是控制来自 Git 推送的自动部署，并标为 deprecated，建议使用后两项更精细的设置。**这是配置不一致的直接证据，不是已确认的 Cloudflare 内部因果分析**；不能据此断言旧开关必然导致下列排队条目。

## 三、旧 GitHub Origin 与新 Cloudflare Origin 的本质区别

**原 Staging Auth 授权 Origin：**
`https://myintmoehein0115024.github.io`

**本次独立 Pages 预览 Origin：**
`https://mmhvault-auth-qa-locked.pages.dev`

两个主机不相同，安全隔离是有意设计的，并非用户登录故障：
- Staging 主 Edge `mmh-n10a6-username` v11 固定 `ORIGIN='https://myintmoehein0115024.github.io'`；
- 真实 SDK 桥 `N10-A7.27-staging-ephemeral-sdk-LOCKED.cjs` 验证传入 Origin 必须严格等于旧 GitHub Origin，且默认 `STAGING_SDK_BOOTSTRAP_ENABLED=false`；
- `N10-A7.23` 实际控制器要求相同 Staging 项目/Origin 且默认 `ALLOW_REAL_OPERATIONS=false`；
- 真实 Turnstile 服务器校验绑定 `hostname='myintmoehein0115024.github.io'`，而不是新 Pages hostname，并且绑定/登录使用不同 Action；
- Cloudflare Pages 锁定预览的真正 HTTP CSP 明确 `connect-src 'none'`、`frame-src 'none'`，浏览器已经在 N10-A7.33 的公网 Chromium 测试中证明无法连接 Supabase。

因此**不能通过“仅把页面按钮启用”来做真实登录**，也不能把 Pages URL 当成现有 Staging 登录 Origin 的自然替代。

真正的 Origin 迁移需要另外一份批准的 Staging 专用、测试窗口有限的完整变更设计：精确的目标测试主机、真实密码页面的响应级 CSP、安全托管、SDK 受限请求路径、Edge CORS、Turnstile sitekey/Hostname/Action、旧账号 UID/RLS 对照、一次性验证码、速率限制、Secret 与回滚。正式域名 `mmhvault.com` 不属于此次迁移范围；不能把 Staging 密钥带到正式站点。

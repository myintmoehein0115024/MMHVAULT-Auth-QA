## 四、回滚策略：不删除、不断账、不覆盖其他工作

1. **发布前**：记录正式 `login.html` 和其他将改动文件的实际 Git SHA 及当前 HEAD，测试旧邮箱/Google/恢复/财务/账户切换；备份当前完整源文件和所依赖的独立资源文件。不得把 Staging 测试账户当生产数据。
2. **异常触发**：发现 UID 错配、旧账户数据在新会话出现、登录会话签发异常、密码恢复绕过、RLS 拒绝或财务余额错误，立即暂停新入口并触发回滚；不要等用户投诉。
3. **回滚**：先关闭新增入口及服务器激活闸门，再从审核的 Git 提交回退仅本次变更的 `login.html` 和新增 JS/CSS 引用。**不进行 force-push，不覆盖其他开发者新提交**。新增的独立文件在确认无被引用后再单独清理。
4. **禁止**：不得删除/清空 `auth.users`、用户名映射、RLS 策略、设备授权或财务记录；不自动重置 Secret、Crypto 本金、Transactions、Accounts、Invest、Wish Fund。
5. **恢复验证**：使用真实受控测试账户验证邮箱、Google、重置密码、原 UID、登录会话和账户切换；检查 Dashboard、Transactions、Invest 数字与回滚前基线一致。
6. **收尾**：生成故障原因及影响记录；仅在问题修复并重新完成验收后考虑下一次发布。

## 五、必须由用户明确确定的规则

**密码规则**：正式页现在注册 min6、设置修改 min8、邮件重置 min10；用户曾计划新账户密码 6–20。Supabase 官方文档不建议低于 8 位，并提供泄露密码保护（取决于套餐）。在发布之前，需要确定统一的新密码规则与历史密码兼容，不得未经用户确认偷偷改变已有密码。官方文档：[Supabase Password Security](https://supabase.com/docs/guides/auth/password-security)。

**设备绑定**：旧设备授权应继续保持相同门槛；用户名登录新增后不能形成第二套可信设备，既有设备不应被自动解除授权。

**普通登出**：现有 `app.html` 某些按钮调用 `db.auth.signOut()`，该方法默认可能退出全部会话；在下一阶段设计中须明确区分“本设备退出 / 其他设备退出 / 全部设备退出”，不得以更改登录方式为由改变现有用户预期。

## 二、真实阻断：Cloudflare Access（Zero Trust）未启用

读取 `GET /accounts/{account_id}/access/apps` 时，Cloudflare 明确返回：

`HTTP 403 / code 9999 / access.api.error.not_enabled`。

Cloudflare 返回的说明是：`Access is not enabled`，需要先到 Cloudflare Dashboard 点击 **Enable Access**。连接已具有 `access.read/write/revoke`，**重新连接插件不会解决**。

因此即使 Pages 项目已经创建，**它尚不具备被证明有效的私有入口保护**。不能将独立的凭据页面发布到公网，不能声称“私有网站已上线”。

**用户现在只需完成一项前置操作**：在 Cloudflare 账户 Dashboard 打开 Zero Trust/Access，按提示完成首次启用。

参考官方文档：
- https://developers.cloudflare.com/cloudflare-one/setup/
- https://developers.cloudflare.com/pages/platform/known-issues/
- https://developers.cloudflare.com/pages/configuration/preview-deployments/

注意官方 Pages 对保护 `*.pages.dev` 的特殊说明：
1. 在 **Workers & Pages** 选择新项目，进入 **Settings → Enable access policy**；此按钮只有 Access 已启用并配置成功才可实际完成。
2. 到 **Zero Trust → Access controls → Applications** 复核 Access 应用保护的准确主机名。
3. 对 `pages.dev` 根主机与预览/唯一部署子域 `*.<project>.pages.dev` 需分别复核；官方 Known Issues 描述了移除 wildcard `*` 后再次启用 preview policy 的操作方式。
4. 访问策略应是**仅已有指定测试人员的精确邮箱**，默认拒绝所有其他访客；不能用公开 Everyone 策略，不允许无登录绕过。
5. 在真实上线任何 credential-enabled 页面之前，须通过未认证访问验证主站/唯一部署 URL/preview URL 均被 Access 阻断，且登录页 HTTP 安全头、CSP、日志不泄露 JWT/密码。
6. Cloudflare Access 保护**浏览器托管站**，不自动等于保护 Supabase Edge API。未来 Edge 仍需自有服务端验证、限时开窗、OTP/CAPTCHA、Uid/RLS、rate-limit；不要把浏览器 CORS 当作后端身份认证。

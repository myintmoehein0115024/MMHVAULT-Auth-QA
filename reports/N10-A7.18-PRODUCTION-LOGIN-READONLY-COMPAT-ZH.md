## 二、原有功能与必须保留的安全约束
1. 邮箱密码使用 Supabase `signInWithPassword`，Google 使用 `signInWithOAuth`，邮箱注册使用 `signUp`；新用户名模式是**同一 Auth UID 的别名**，不能另建一个用户名 UID、不能将转账/账户/投资数据按邮箱重新归属。
2. 登录后 `verifiedRedirectV946` 必须在 `getUser()` 验证远程 UID 与 `getSession()` 缓存 UID 一致后才跳转。Google OAuth callback 未完成时禁止自动跳转；仅允许白名单 `app.html` 和 `business.html`。
3. 密码重置只响应真正的 `PASSWORD_RECOVERY` 事件，比较恢复会话 UID 与 Auth UID，不能被 `?recovery=1` 等 URL 参数冒充。
4. 主财务 `app.html` 启动时再次向 Supabase 验证 UID，并在账号切换时先显示 `mmhP947GuardV947` 遮罩、清理旧数据、重新加载新账号云端内容。不能绕过该流程，否则有跨账户旧数据残留风险。
5. 设置中的密码修改使用独立 `persistSession:false` 验证客户端和当前 UID 双检；支持退出其他设备以及退出全部设备，必须保留。
6. 中英语言切换入口、现有导航回跳、iPhone Safari / Android Chrome 响应式行为保留。
7. 新用户名接口返回的会话只能进入**同一 Supabase 项目的 Auth 客户端**，正式项目不能安装 Staging JWT 或使用 Staging 的 Edge URL；必须调用 `auth.setSession` 后再分别调用 `getUser` / `getSession` 比对 UID，最终复用 `verifiedRedirectV946`。

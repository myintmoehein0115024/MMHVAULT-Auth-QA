## 五、真实 G10/G11 前所需的变更顺序与停止条件

**A7.38 的完成不等于 A7.39 已获授权。** 在真正启动任何真实账号之前，需要：
1. 决定是沿用新 `pages.dev` 还是使用另一个独立的凭据型 QA 域名。当前锁定页不能直接开启密码输入，否则会破坏其无外联 CSP 和承诺的安全边界。
2. 以单次明确范围更新 Staging 的允许 Origin（候选代码见 N10-A7.36），严格阻止 `mmhvault.com` 和旧未经批准的 origin。任何多来源并存都必须明确审核。
3. 对 Turnstile Widget 的允许 hostname 做适当 Staging 专用变更，或者创建专用 QA Widget。将来 Siteverify 服务端仍须精确核验请求的 hostname 和 `mmh_n10a6_bind` / `mmh_n10a6_login` Action，且必须检查一次性 HMAC token 防重放与速率限制。
4. 适配受限 Staging SDK/浏览器客户端，并建立真正具有 HTTP 响应级 CSP 的独立凭据安全网页。禁止凭据持久化、跨会话泄露、跨项目 Token、生产后端访问。
5. 受控真实账户测试必须经授权，精确 UTC 窗口不超过 15 分钟，指定已有 Staging 用户与可撤回的别名；不得在正式站执行。
6. 先备份并核查 Edge v11 源码哈希、Secret、数据计数、RLS 和回滚能力；禁止启动注册或直接操作资金数据。
7. 实际 G10/G11 通过后，先本地退出、回滚硬锁/Origin/Window、证实 Secret 已关、重复核对账号/别名/限流，再更新签署 PASS 证据。任何一处失败都应关闭测试并保留 BLOCKED。
8. `auth_leaked_password_protection` WARN 应列为正式三登录上线安全整改复核项，是否/如何启用需结合 Supabase 当前 Auth 设置评估，不能因它是 WARN 就绕过测试。
